# ADR-001：渲染后端选择（Canvas 2D vs WebGL 2）

状态：**已确认（2026-11-04，实机基准数据闭环）** ｜ 日期：2026-11-04 ｜ 版本：v0.7.0

## 实测结论（v0.7.1 回填）

实机（1280×679 @ DPR 2，Edge 156）：渲染 3.0 ms/帧（默认规模）、3.0–3.1 ms（Boids 至 1200 粒子），全部远低于 8 ms 触发线；默认规模 FPS 59.7–60.0。瓶颈实测在模拟侧（PL 的 O(n²)），与决策前提一致——**Canvas 2D 维持，WebGL 2 议题关闭**，仅保留"未来需求 > 2000 粒子"一条远期触发条件（届时需先解决模拟扩展性）。

## 背景

技术设计文档 §8 预设："若 Canvas 2D 不达标则实现 WebGL 2 渲染后端（模拟零改动）"。Renderer 接口（`render(state, alpha)` + `updateVisual`）自 M0 起即为后端无关设计。

## 决策

**默认规模（PL 500 / Boids 300，1920×1080，60 FPS）下维持 Canvas 2D**；满足下列任一触发条件时再实现 WebGL 2 后端：

1. `?bench=1` 实测渲染 CPU 耗时 > 8 ms/帧，或
2. 实测 FPS < 55，或
3. 未来需求要求 > 2000 粒子（模拟侧 O(n²) 会先成为瓶颈，见性能报告 §3，需先解决模拟扩展性）。

## 理由

- 视觉管线已通过结构性手段控制在低成本区：光晕层 1/4 分辨率、DPR ≤ 1.5、无逐粒子 shadowBlur、两遍合成限曝。瓶颈设计上是 fill-rate 而非状态切换，Canvas 2D 的 drawImage 精灵路径对此友好。
- WebGL 2 后端的成本不止实现：发光混合（additive glow）在 GL 中需自写混合管线与拖尾 framebuffer，两遍合成的视觉调参成果（密度感知调光、抖动防色带）需在新后端重新校准——为一个未证实存在的瓶颈提前付这笔账不划算。
- 模拟/渲染解耦意味着切换后端的集成成本被接口封死，推迟决策没有架构债。

## 触发后的实施要点

- 新后端实现 `Renderer` 接口，主画布合成路径替换为 GL：离屏发光 framebuffer（1/4 分辨率）+ additive blending + 全屏拖尾 quad。
- 密度感知调光在顶点/片元 shader 中用粒子密度属性复现同一公式 ÷(1+density)。
- 色带抖动在片元 shader 中用 hash noise 复现。
- 验收标准 = 与 Canvas 2D 版逐帧对比平均绝对色差 < 2/255（视觉差异不可辨）。
